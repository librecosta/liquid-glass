## Owner actions before publication

- [ ] **npm identity/scope:** sign in on your own machine and verify `npm whoami --registry=https://registry.npmjs.org`. Confirm that npm `@librecosta` is your user/organization scope and that the publishing account/team has package-write permission. GitHub organization ownership does not establish npm ownership. On 2026-11-05 this machine returned `ENEEDAUTH`; public package lookup returned 404, which does not prove name availability or scope control.
- [ ] **Account security and access:** verify your npm account email, enable/confirm account 2FA and complete the registry's publishing authentication requirements. Confirm a scoped **public** package is intended. Do not put tokens/OTP in the repository, issue or chat. See [npm scoped publishing](https://docs.npmjs.com/creating-and-publishing-scoped-public-packages/).
- [ ] **Photo rights:** retain the original photo/source page and license/CC0 evidence for the exact forest file, or approve replacement with confirmed material. The earlier owner-supplied CC0 report is recorded in [provenance](../src/assets/forest.provenance.json); original rights are not independently verified. The source repository MIT is not evidence for the photo. This gate applies to public demo hosting and wider promotion of derived README screenshots; forest/screenshot binaries are excluded from npm.
- [ ] **RC approval:** review the installed package and production preview, then explicitly approve any `main` promotion, removal of the publish lock and actual npm/Tag/Release operations. None are authorized by this task.

## Sequence after separate owner approval

1. Resolve npm ownership/security and image rights; review the RC, approve the exact source commit and any merge to `main`.
2. Remove `private: true` deliberately in a reviewed change, rerun `npm ci`, `npm run check` and `npm pack --dry-run`, and inspect the exact final tarball. The RC tarball still contains the publish lock; do not mistake it for an approved publish artifact.
3. Only after explicit publication approval, have the authorized owner publish the reviewed `0.1.0` package as public to the official registry. Reinstall that exact registry version in a fresh consumer and verify exports, types, SSR, Hook and license. No `npm publish` command has been executed in this task.
4. Only after the registry result is known, update both READMEs/CHANGELOG from RC wording, and separately approve the `v0.1.0` tag and GitHub Release using the draft text. Do not tag an unpublished/failed candidate as a completed release.
5. Independently approve and configure Pages after photo clearance; verify both languages/entries at the real project URL before advertising it.

Real Safari/Firefox, physical touch devices and assistive-technology combinations still need broader coverage. RC tests are not a claim of universal browser or production stability.

## Registry commit metadata discrepancy

Registry `gitHead` is **`0f6d1500d1ec5aa5295a3fc7774ec3c1d596ae2f`**, the dev parent of the authorized main merge, rather than `723201c`. Both commits have the exact complete Git tree **`015aed86bb0775c0188f1043f4a6c6612efad643`**. The publish command ran from the authorized main checkout and its approved archive integrity matches the official Registry archive exactly.

The installed npm 9.6.7 `read-package-json` implementation reads `.git/HEAD` as a directory path and walks parents on failure. The nested detached worktree has a `.git` **file**, so this resolution reached the enclosing dev checkout. This explains the recorded dev SHA; it does not change package files. Do not claim that Registry's exact commit metadata matches main or attempt to overwrite/republish immutable 0.1.1.

The unmodified `npm run test:consumer -- --registry` correctly **failed its strict gitHead assertion**. A one-off ignored verification runner then executed the same consumer suite with this discrepancy explicitly recorded, requiring the exact two known SHAs, their complete approved tree and the exact approved archive SHA-512. It also required full Registry/local archive equality before proceeding with all normal install/type/license/browser checks. Those checks passed; the committed general verifier was not relaxed. Local evidence is `test-results/registry.json` in the frozen release checkout, including `exactCommitMetadataMatches: false` and `archiveMatchesSource: true`.

For future releases, use a clean standalone checkout outside another repository and verify npm's resolved manifest `gitHead` before publication. Each future publication still requires explicit owner authorization and owner-operated 2FA.
